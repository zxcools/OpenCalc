## 一、缺陷

### B1（P1）详情页/主表的日期没有转义 → 存储型 XSS
- 位置：`main.py:7671-7674`（`fmtDate`）/ `8479`、`8482`、`8179`、`8183`、`8581`（内插点）
- 现象：`fmtDate` 对**不匹配** `^\d{4}-\d{2}-\d{2}$` 的串**原样返回**，随后被直接内插进 `innerHTML`：
  ```js
  fmtDate(d){ if (!d) return '—'; if (/^\d{4}-\d{2}-\d{2}$/.test(d)) return d; return d; }
  ```
  ```js
  &nbsp;开仓时间 <b>${this.fmtDate(d.open_date)}</b>
  ```
- 写入侧也没有校验：`trade_upsert`（`2942-2954`）只对 `open_time/close_time` 做 `.strip()[:5]`，`open_date/close_date` 完全不管；`trade_import_record`（备份导入）同样不校验。
- 触发路径：手工构造一份 `.opcalc` 备份导入，或直调 `/api/trades/upsert` 把 `open_date` 写成 `<img src=x onerror=…>` → 打开详情页即执行。**本机自用 + 需要主动导入才触发，所以定为 P1 而不是 P0**，但修起来只有一处。
- 建议：`fmtDate` 在返回非日期串前先 `escHtml`（合法日期只含数字与连字符，不会被影响）；同时在 `trade_upsert` / `trade_import_record` 里对 `open_date/close_date` 做一次格式校验（非法就拒绝或留空）。
- 同类：`showError(d.error || '计算失败')` 也是往 `innerHTML` 写（`7075`，调用点 `6807/6945/7036`）。当前 error 文案都是后端常量，风险低，但建议一并改 `textContent`。

### B2（P2）手续费口径选「不计算」时，弹窗与详情页口径不一致
- 位置：`main.py:3395-3399`（`fee_estimate` 硬编码 `FEE_MODE_EX`）、`9149`/`9193`（`syncModalFee`/`_paintModalFee` 不看 `feeMode`）、`8268`（`feeMetaExtra` 会因 `feeMode==='off'` 整行隐藏）
- 现象：切到「不计算」后，**详情页顶部的「手续费合计 / 净盈亏」整行消失**，但**开仓/平仓弹窗照旧显示金额**（实测 `fee_estimate("rb","rb2701",qty=5)` → `fee_open=3.55`）。
- 这不算算错，是**同一件事两处口径不同**。建议二选一：
  - (a) 弹窗保留金额，但在后面加一句「当前口径为「不计算」，未计入净盈亏」；
  - (b) 跟随口径：`off` 时弹窗也不显示金额。
  - 我倾向 (a) —— 费率差额是你选平今/平昨的依据，藏起来反而不好用。

### B3（P2）风险条的「保证金按 16% 估」会说错
- 位置：`main.py:3377`（顶层 `"margin_rate": DEFAULT_MARGIN_RATE` 恒定）、`3352`（逐笔占用用的是该记录自己的 `h["mr"]`）、`8119`（前端文案「保证金按 {margin_rate}% 估」）
- 现象：记录里若带 `calc_json.margin_rate = 0.22`（例如测算时把保证金率改成 22%），**占用金额按 22% 算，但旁边小字仍写「按 16% 估」** —— 数字和说明互相矛盾。
- 相关精度问题：同一合约多次开仓时，`g["mr"]` 会被**最后一次**开仓记录的保证金率覆盖（`3254`），即全部手数都按最后那次的率算；中途改过保证金率就会有偏差。
- 建议：后端顶层改成返回实际用到的保证金率集合（如 `used_rates` / `has_custom_mr`），前端文案改为「按记录里的保证金率估（其中 N 笔为自定义 22%）」；`g["mr"]` 改成按手数加权或逐笔算。

### B4（P2）`/api/funds/backup-diff` 只捕 `ValueError`，真实异常会逃出请求处理器
- 位置：`main.py:3974-3976`（`except ValueError`）、`1476`（对**当前库**以只读 URI 打开）
- 现象：当前库文件不存在（数据目录被手工删掉/网盘未同步下来）或损坏时，`sqlite3.connect("file:…?mode=ro")` 抛的是 `sqlite3.OperationalError`（实测确认类型），**不被 handler 捕获**；而 `do_GET`（`3845`）没有最外层 try → 异常冒到 socketserver → **连接直接断开、浏览器报 `Failed to fetch`**，而不是给出「差异取不到，仍可恢复」的提示。
- 建议：该 handler 改成 `except Exception`（把原异常文案带进 `error`）。同类的还有几个带 `try` 的 handler，建议一起看一遍。

### B5（P3）备份的「合并窗口」加了锁，但没真正防住重复备份
- 位置：`main.py:1295-1299`（锁内检查窗口）、`1316-1319`（快照**做完之后**才写 `_last_backup_ts`）
- 现象：两个并发写请求都能在第一个锁块里通过「距上次不足 2 秒」的检查，然后各做一次全库快照 → 白占一个轮转位（保留 10 份）。注释里声称要防的正是这件事。
- 建议：把 `_last_backup_ts = now` 挪进第一个锁块（先占坑再干活）。

### B6（P3）`copyText` 兜底路径在异常时不会移除临时节点
- 位置：`main.py:8533-8546`
- 现象：`execCommand('copy')` 或 `select()` 抛异常时，`document.body.removeChild(ta)` 被跳过、`catch` 里也没有回收 → 每次失败在 `body` 里残留一个隐藏 `textarea`。返回值 `false` 本身是对的。
- 建议：`try/finally` 里移除。

### B7（P3）`_close_fund_conn` 关的是「全局连接」，与注释不符
- 位置：`main.py:2048-2054`（关全局 `FUND_DB_CONN`）、`2084`（在锁**外**写入全局）、`1814`（只剩一个 `global` 声明）
- 现象：注释写「连接其实是每线程一个(`_DB_LOCAL`)，这里只关当前线程这个」，但代码关的是**全局**那个、而全局是被「最近一次调用 `_fund_db()` 的线程」覆盖的 —— 可能是别的线程的连接。`_fund_db` 里虽然有一次 `SELECT 1` 探活（`2075-2078`），但从探活到 `_db_ensure_schema`（`2087`）之间仍有窗口，换库动作插进来时该线程会拿到/使用已关闭的连接。
- 建议：`_close_fund_conn()` 改成关当前线程的 `_DB_LOCAL.conn` 并清空，顺手把 `FUND_DB_CONN` 这个历史全局删掉（现在 4 处引用里 3 处是它自己）。

### B8（P4）零碎
- `main.py:3827` `return open(fp,"rb").read()` —— 句柄未显式关闭（靠引用计数回收），改成 `with` 更稳。
- `main.py:416` `trade_day` 的时间正则要求**两位分钟**：`"21:5"` 匹配失败 → 当白盘返回（本应夜盘顺延）。UI 是 `type="time"`，实际到不了，属边缘。
- 前后端契约上有几个「后端返回、前端没用」的键：`fee_estimate` 的 `code/is_option/mult`、`backup-diff` 的 `tables/span/current_span`、`detail` 的 `fee_mode/open_day/close_day`。不是缺陷，留给后续功能用或清理。

## 二、已核查、确认没问题（省得以后重复排查）

- **交易日历数据正确**：`MARKET_HOLIDAYS` 与《国务院办公厅关于 2026 年部分节假日安排的通知》**逐条一致**（另行独立核对过：元旦 1/1–1/3、春节 **2/15–2/23 共 9 天**、清明 4/4–4/6、劳动 5/1–5/5、端午 6/19–6/21、中秋 9/25–9/27、国庆 **10/1–10/7**；2025 各段同样吻合）。表里虽然收录了周末，但 `is_trading_day` 先判 `weekday()>=5`，不影响结果；**调休补班的周六周日不开市**这点也符合期货市场实际。
- **`trade_day` 边界实测正确**：跨年夜盘（2025-12-31 21:30 → 2026-01-05）、长假前夜（2025-09-30 21:30 → 2025-10-09）、长假首日 21:00 后、周日凌晨 01:00（→ 顺延到周一）、周五夜盘跨周六 —— 5 组全对。
- **`calc_json` 解析不会炸**：`"{bad json"` / `"[]"` / `'"str"'` / `'{"margin_rate":"0.3"}'` 逐个试过，都落到默认 16%，没有异常漏出。
- **`fee_estimate` 边界**：`qty` 为 0 / 负数 / None → 0；`price` 为 None → 只剩申报费；mode 非法 → 内部按期货处理（HTTP 层还有 `_mode_arg` 归一）。HTTP 层已对 `price/qty` 做 `float()` 并兜住，线上不可达非数字入参。
- **`fund_backup_diff` 对旧备份安全**：缺表时逐表 `try` 返回 None，文案会写「这份备份缺这张表」；`fund_backup_list` / `fund_backup_diff` / `fund_restore_backup` 的只读连接都有 `finally`（v50.77 补的）。
- **新前端代码**：`copyText` 的 Clipboard 分支、`ocToast` 的元素复用与定时器、`.copyc` 的 `data-copy`（走 `escHtml`，含 `& ' " <` 都安全）、点击委托只绑一次（`TradeUI.init()` 全流程只跑一次）—— 都没问题。
- **无死代码/重复定义**：全仓库（含 `tests.py`/`tools`/`oc_cdp_test.js`）查过，没有「定义后从未被引用」的函数；v50.77 删掉的 `_looks_variety` 确认删净。（上一轮我曾误判 `fund_clear_all` / `detect_call_put` 是死代码，原因是只搜了 `main.py`，这次把测试与工具脚本一起搜了。）
- **36 处 `except ... pass` 逐条看过**：包住写操作的只有 `_write_backup_meta`（写 sidecar 说明，注释已声明故意静默）、`_db_ensure_schema` 的 `commit`、轮转/半成品删除几处；都属于「失败不影响主流程，且有备份兜底」的既定设计，不是漏网。

## 三、可优化的功能（按性价比排序，我的推荐在最前）

1. **「复制为复盘表格」**（推荐，成本低）
   你每天复盘是固定 6 列（时间 / 品种 / 合约 / 操作 / 平仓原因 / 平仓盈亏）。上一版刚做好「点合约复制」的底层能力（`copyText` + 轻提示），再往前一步就能一键把选定范围的操作导出成 **Markdown 表格**直接粘进知乎/文稿。跨夜盘标注「昨夜盘」这类规则先不自动化，留给你自己改。

2. **持仓盯盘条**（推荐，价值最高）
   风险条现在只讲「占用多少钱 / 最大亏损多少」。你走的是**跟踪止损**，最需要的是盘中的三个数：**最新价 / 浮动盈亏 / 距初始止损还有多远**。项目里已经有行情接口（新浪，前端 10s 刷新），接上去成本不高，盘中一眼就知道该不该动手。

3. **交易日历年度提醒**（推荐，成本极低）
   目前唯一的「每年手工维护」隐患。启动时若**当前年份不在 `MARKET_HOLIDAYS` 里**，在数据位置那儿黄字提示一次「2027 年放假安排还没录入，平今/平昨会退回只跳周末」。这样通知一发出来就不会漏。

4. **导出当前筛选为 CSV**：主表筛选/统计区间选定后一键导出，给复盘和月度统计取数。
5. **品种盈亏排行**：按品种（或按月）的 胜率 + 净盈亏 + 手续费小表，贴合你按品种跟踪的习惯。
6. **主表点列头排序** / **自定义区间（起止日、季度、半年）** / 平仓弹窗把两档手续费的**差额**也写出来（如「平昨比平今贵 ¥8.60」）。
7. **健壮性兜底**：给 `do_GET` / `do_POST` 加统一的最外层 try，异常时返回 `{"ok":false,"error":…}` 并在服务端打印堆栈 —— 避免以后再出现「某个接口 500 变成 Failed to fetch、还看不出是哪条」（B4 就是这类）。
